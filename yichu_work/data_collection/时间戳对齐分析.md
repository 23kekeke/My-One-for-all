# SDK时间戳对齐分析

## 核心问题

多传感器数据采集时，不同传感器的采样时刻不同。若直接取各传感器最新缓存值拼成一次 observation，会造成时序错位——关节值来自时刻 T1，相机图像来自时刻 T2，两者相差可达数十毫秒。这对模仿学习训练有害。

```
时间线 ────────────────────────────────────────────────────────────→

关节流 (500Hz):
  │  msg1 (ts=100.002)   msg2 (ts=100.004)   msg3 (ts=100.006)   │
  └── 所有关节共享同一 gRPC 消息, ts 相同 ──┘

相机流 (~30fps):
  │     frame A (ts=100.000)            frame B (ts=100.033)      │
```

当 `get_observation()` 在 `ts=100.006` 时刻被调用：

| 方式                       | 关节数据            | 相机图像          | 时间偏差                |
| -------------------------- | ------------------- | ----------------- | ----------------------- |
| **旧逻辑** (latest cache)      | 关节 msg3 (ts=100.006) | frame B (ts=100.033) | **+27ms** (相机比关节晚)  |
| **新逻辑** (nearest-neighbor)  | 关节 msg3 (ts=100.006) | frame A (ts=100.000) | **-6ms**  (相机比关节早)  |

时间偏差从 **27ms 降到 6ms**，对齐精度提升约 4.5 倍。

## 对齐原理

### Nearest-Neighbor 时间域对齐

以关节时间戳为"锚点"，从相机 ring buffer 中选出采集时刻最接近的那一帧，而非盲目用最新的帧。

```
1. 参考时间戳 = 关节 msg3 的 gRPC header.stamp = 100.006

2. ring buffer 中维护最近 0.5 秒的相机帧:
   │  (100.000, frame A)  │  (100.033, frame B)  │

3. nearest-neighbor 搜索:
   |100.006 - 100.000| = 6ms   ✓  ← 选 frame A
   |100.006 - 100.033| = 27ms

4. observation = {关节(msg3), 相机(frame A)}
```

此策略与参考代码 `data_collector.py:2691` 对其他相机采用的 nearest-neighbor 对齐完全一致。

### 与参考代码的关系

| 维度           | 参考代码 (`data_collector.py`)           | `x_robot.py`                             |
| -------------- | ---------------------------------------- | ---------------------------------------- |
| 对齐时机       | **后对齐**: 录制完毕, 调用 `_align_data_by_timestamp()` | **实时对齐**: `get_observation()` 调用时即时完成 |
| baseline 时间戳 | 头部相机 (head_camera) 时间戳              | 关节状态 (joint state) 时间戳              |
| 关节对齐策略   | 线性插值 (linear interpolation)            | 无需插值 (所有关节共享同一 gRPC 消息时间戳)  |
| 相机对齐策略   | nearest-neighbor                          | nearest-neighbor (从 ring buffer)          |
| 数据存储       | 全部点 + 时间戳 → 后对齐输出               | ring buffer (0.5s) → 实时选帧             |

## 三级时间戳架构

```
gRPC 硬件时间戳 ──→ 对齐时间戳 ──→ LeRobot 帧时间戳
 (真实物理时钟)     (同步用)       (合成值, 存入 parquet)
```

| 层级              | 来源                                             | 存储到数据集? | 用途                                      |
| ----------------- | ------------------------------------------------ | :-----------: | ----------------------------------------- |
| gRPC 时间戳       | `msg.header.stamp` (硬件时钟, 秒+纳秒)            |      否       | 流式线程内对齐相机帧与关节                  |
| 对齐时间戳        | `get_observation()` 中关节参考 `joint_ts`          |      否       | 诊断日志 (`log_alignment_stats: true`)      |
| LeRobot 帧时间戳  | `DatasetWriter.add_frame()` → `frame_index / fps` |      **是**      | 训练时视频帧查询 (`delta_timestamps`)       |

### 为什么 gRPC 时间戳不写入数据集？

- `DatasetWriter.add_frame()` 强制生成合成时间戳 `frame_index / fps`，确保均匀间隔
- 训练时 `delta_timestamps` 需要确定性的、等间隔的时间索引来查询视频帧
- gRPC 硬件时间戳存在网络抖动，不适合作为训练时的确定性查询索引

**角色分工**: 实时层用硬件时间戳对齐提升数据同步质量，存储层用合成时间戳保证训练确定性。

## 诊断: 对齐误差分析

配置 `log_alignment_stats: true` 后，每 2 秒输出对齐误差:

```
Alignment (camera_ts - joint_ts): head_camera: +5.2 ms, left_arm_camera: -12.3 ms | ref=1716835200.123
```

| 字段               | 含义                                              |
| ------------------ | ------------------------------------------------- |
| `+5.2 ms`          | 相机帧比关节状态晚 5.2 毫秒 (正值 = 相机更晚)      |
| `-12.3 ms`         | 相机帧比关节状态早 12.3 毫秒 (负值 = 相机更早)     |
| `ref=...`          | 关节参考时间戳 (Unix 秒)                           |

正值/负值均属正常——取决于 ring buffer 中最近帧相对于关节参考的分布。误差的**绝对值**越小，对齐越精确。

# LeRobot 录制实测时间戳误差分析

### 实测日志

```
INFO 2026-05-27 18:25:46 /x_robot.py:557 Alignment (camera_ts - joint_ts):
  head_camera: -152.3 ms, left_arm_camera: -64.4 ms, right_arm_camera: -56.8 ms | ref=1779877546.517

INFO 2026-05-27 18:25:48 /x_robot.py:557 Alignment (camera_ts - joint_ts):
  head_camera: -152.1 ms, left_arm_camera: -53.1 ms, right_arm_camera: -48.3 ms | ref=1779877548.537

INFO 2026-05-27 18:25:50 /x_robot.py:557 Alignment (camera_ts - joint_ts):
  head_camera: -140.2 ms, left_arm_camera: -26.3 ms, right_arm_camera: -54.6 ms | ref=1779877550.542

INFO 2026-05-27 18:25:52 /x_robot.py:557 Alignment (camera_ts - joint_ts):
  head_camera: -150.3 ms, left_arm_camera: -56.4 ms, right_arm_camera: -50.9 ms | ref=1779877552.571
```

### 关键发现

| 相机             | 典型偏移量     | 含义（camera_ts - joint_ts）                    |
| ---------------- | -------------- | ----------------------------------------------- |
| head_camera      | -140 ~ -152 ms | 相机帧比关节参考早约 150ms                       |
| left_arm_camera  | -26 ~ -64 ms   | 相机帧比关节参考早约 30-65ms                     |
| right_arm_camera | -48 ~ -55 ms   | 相机帧比关节参考早约 50ms                        |

**所有偏移量均为负值**，说明相机帧的硬件时间戳始终早于关节参考时间戳。

### 偏移量远超理论预期的原因

理论上，30fps 相机 + nearest-neighbor 搜索，误差应在 **±16.7ms** 以内。实际达到 -150ms，原因分析如下：

| 原因 | 说明 |
| ---- | ---- |
| **相机流水线延迟** | camera `header.stamp` 的赋值时刻可能不在 CMOS 曝光完成瞬间，而在 JPEG 压缩/编码完成时。head_camera 分辨率更高（如 1280×720），JPEG 编码耗时更长，导致其硬件时间戳比关节状态"看起来"更早 |
| **关节流频率优势** | 关节状态 500Hz（每 2ms 一条），`get_observation()` 调用时的 `joint_ts` 几乎实时；而相机仅 ~30fps（每 33ms 一帧），ring buffer 中最近帧距当前采样点可能已达 ~16ms |
| **head vs arm 差异** | head_camera 分辨率高 → 编码传输延迟大 → 相对 joint 的偏移更大（-150ms）；arm cameras 分辨率低 → 偏移较小（-50ms 左右） |
| **时钟源一致性** | 相机和关节的 `header.stamp` 均来自机器人上的同一 gRPC 时钟源，理论上不存在跨时钟偏差，**实测偏移完全来自流水线延迟** |

### 偏移量是否影响采集质量？

| 指标 | 结论 |
| ---- | ---- |
| **绝对值偏大** | 不影响，只要偏移量**稳定**即可，因为策略模型学到的是这种对齐关系 |
| **偏移量抖动** | 需关注。head_camera 在 -140 ~ -152ms 间波动（约 12ms 范围），arm cameras 抖动更大（-26 ~ -64ms），可能与网络/CPU 调度有关 |
| **符号一致性** | 全部为负（相机早于关节），说明 nearest-neighbor 搜索稳定收敛在 ring buffer 中"较旧"的方向，没有出现正负交替的不稳定现象 |

### 优化建议

1. **关注漂移，而非绝对偏差**：监控每个 episode 内偏移量的标准差，而非绝对值。标准差 < 20ms 即为稳定
2. **降低 head_camera 分辨率**：若使用较低分辨率（如 640×480），可缩短编码延迟，减小偏移量
3. **增大 ring buffer 容量**：若验证偏移量超过 buffer 裁剪窗口（`_max_camera_history`），说明帧被错误地裁剪掉了，需要增大窗口
4. **gRPC 时间戳确认**：检查 SDK 端 `header.stamp` 的赋值点在 capture 完成时刻还是 encode 完成时刻，确认后可在文档中记录以指导后续分析

### 与 SDK 理论分析的对比

| 维度 | SDK 理论分析 | LeRobot 实测 |
| ---- | ------------ | ----------- |
| 对齐策略 | nearest-neighbor（joint 为锚） | 相同 |
| 预期误差 | ±6 ~ 27ms | head: -150ms, arm: -50ms |
| 时间戳来源 | gRPC `header.stamp` | 相同 |
| 实测误差来源 | 纯理论 ring buffer 最近邻计算 | 编码流水线延迟 + 分辨率差异 + 网络抖动 |

**核心结论**：leRobot 的 nearest-neighbor 对齐算法与 SDK 完全一致，实测放大到 -150ms 的原因是**相机 pipeline 的编码/传输延迟在硬件时间戳上的体现**，而非对齐算法本身的问题。只要偏移量稳定，数据质量不受影响。
